# 微信 AI 接入方案调研：GeWeChat vs 小程序 vs iLink 官方插件

> 日期：2026-09-15
> 关键词：微信机器人、个人号接入、iPad 协议、iLink、OpenClaw、小程序
> 结论速览：做个人微信 AI 助理，**优先用腾讯官方 iLink / OpenClaw 微信插件**（合规、低封号风险）；GeWeChat 逆向协议能用但违规、有封号风险；小程序是另一条官方合规但形态不同的路径。

## 一、背景

从分析开源项目 [`Lsogod/personal-ai-pai`](https://github.com/Lsogod/personal-ai-pai) 的微信接入方式入手，逐步延伸到"个人微信号如何被程序接管"这一核心问题，最终对比了三种接入方案的可靠性与合规性。

## 二、微信开放能力的前提

微信的开放能力分两类，理解这点是判断一切方案的基础：

- **公众号 / 小程序 / 企业微信** — 有官方 API，合规，但都不是你本人那个私人微信号。
- **个人微信号（手机上那个）** — 官方**长期不提供**任何收发消息 API。因此任何"让个人微信变机器人"的方案，本质都是绕过官方（逆向协议），直到 iLink 出现才有了官方通道。

## 三、三种方案横向对比

| 方案 | 底层协议 | 合规性 | 封号风险 | 是否需自建网关 | 代表实现 |
|------|---------|-------|---------|--------------|---------|
| GeWeChat | 逆向 iPad 客户端协议 | ❌ 违反用户协议 | 高 | 需 Docker 容器 | personal-ai-pai |
| 微信小程序 | 官方小程序 API | ✅ 合规 | 无 | 不需要 | personal-ai-pai |
| **iLink 官方插件** | **iLink 官方 Bot 平台协议** | ✅ 合规 | **低** | 不需要，直连官方 | Tencent/openclaw-weixin |

## 四、方案一：GeWeChat（逆向 iPad 协议）

### 4.1 什么是"iPad 协议"

微信有手机、电脑版、iPad 版等多个客户端，每个登录后都用**私有加密协议**与微信服务器通信。"iPad 协议"指有人**逆向破解了 iPad 版微信的通信协议**，用程序模拟出一个"假的 iPad 客户端"。

为什么偏偏是 iPad 版：

1. **可与手机同时在线** — 微信允许"手机 + iPad"双端登录，模拟 iPad 端不会把手机顶下线。
2. **协议相对稳定、功能较全** — 收发文字/图片/语音、进群、加好友等。
3. **风控相对宽松**（相对而言，非绝对安全）。

登录方式：程序生成二维码，用真实微信 App 扫码授权，之后"模拟 iPad 客户端"以你的身份挂在微信服务器上代收发消息。

> ⚠️ 这是非官方、违反微信用户协议的做法。风控识别后轻则掉线，重则**封号**（个人号封了基本找不回）。建议只用小号。

### 4.2 GeWeChat 容器(:2531) 是什么

**GeWeChat（Gewe / GeWe）** 是上述 iPad 协议的一个具体产品实现，把逆向协议封装成现成的 HTTP 服务，打包为 Docker 镜像。它充当"翻译中间层"：

```
个人微信 ⇄ 微信服务器 ⇄ GeWeChat 容器(:2531) ⇄ 项目后端
                        (说 iPad 协议)      (说普通 HTTP/JSON)
```

- **容器**：以 Docker 形式运行的独立服务；**:2531** 是其默认监听端口。
- 后端通过 `http://gewechat:2531` 与它通信，脏活（逆向协议）全甩给它。

### 4.3 在 personal-ai-pai 中的实现

- 接收：`POST /webhook/wechat`（`backend/app/api/endpoints/webhooks.py`），`gewechat.parse_event` 做容错式字段提取（`from_wxid`/`from`/`sender` 等多 key 尝试）。
- 发送：`POST {base_url}/sendText`、`/sendImage`（`services/platforms/gewechat.py`）。
- 部署：`docker-compose.yml` 起 `gewe/gewe:latest` 容器。
- **短板**：webhook 端点无签名校验（对比 telegram 端点有 `X-Telegram-Bot-Api-Secret-Token` 校验）。

## 五、方案二：微信小程序（官方合规）

personal-ai-pai 主推的正规方案，实现最完整。

- **登录**：`wx.login` 拿 code → 后端 `POST /api/miniapp/auth/login` → 调官方 `sns/jscode2session` 换 `openid` → 建/取用户发 JWT（`services/platforms/miniapp.py`、`endpoints/client.py`）。
- **access_token 管理**：`MiniappTokenManager` 内存缓存 + 提前 60s 刷新。
- **三种下发**：在线 WebSocket 实时推 / 客服消息 `cgi-bin/message/custom/send` / 离线订阅消息 `cgi-bin/message/subscribe/send`（模板 ID + `thing1`/`time2`）。
- **订阅授权**：小程序侧须先 `wx.requestSubscribeMessage` 由用户主动授权。

## 六、方案三：iLink 官方插件（推荐）

### 6.1 iLink 是什么

2026 年 3 月，腾讯正式推出"微信 ClawBot 插件"，将 OpenClaw AI Agent 集成进微信，底层协议称为 **iLink（智联）**，接入域名 `ilinkai.weixin.qq.com`。这是微信**官方开放给个人号的 AI Bot 能力**，与逆向 iPad 协议性质完全不同。

- 官方仓库：[`Tencent/openclaw-weixin`](https://github.com/Tencent/openclaw-weixin)
- npm 包：`@tencent-weixin/openclaw-weixin`（`@tencent-weixin` 官方命名空间）
- 佐证：`LICENSE` 标注 "Copyright (C) 2026 Tencent"，`package.json` `"author": "Tencent"`。

### 6.2 定位

它**不是独立机器人**，而是 **OpenClaw（AI Agent 框架/网关）的一个 channel 插件**，只负责"微信 ↔ OpenClaw 网关"这一段，AI 逻辑在 OpenClaw 主体。MIT 许可，活跃维护（最新 `2.4.9-beta.0`，2026-09-08），29 个测试文件 + 完整 CI。

### 6.3 架构

```
个人微信 ⇄ 微信 iLink 官方后端            OpenClaw Gateway (宿主)
          (ilinkai.weixin.qq.com)   ⇄   └─ openclaw-weixin 插件
          novac2c.cdn.weixin.qq.com          ├─ 长轮询收消息 getUpdates
                                              ├─ 发消息 sendMessage
                                              └─ 交给网关的 AI/路由/会话
```

关键：**无需自建中间网关容器**，插件直接用 HTTPS+JSON 调腾讯官方 iLink 接口。

### 6.4 核心流程

**登录（官方扫码授权，`src/auth/login-qr.ts`）**

1. `POST /ilink/bot/get_bot_qrcode?bot_type=3` 拿二维码。
2. 终端用 `qrcode-terminal` 画码，真实微信 App 扫码。
3. `GET /ilink/bot/get_qrcode_status` 长轮询状态机：`wait / scaned / need_verifycode / confirmed / expired / verify_code_blocked / scaned_but_redirect(IDC 重定向) / binded_redirect`。
4. `confirmed` 后拿 `bot_token` + `ilink_bot_id`，存 `~/.openclaw/openclaw-weixin/`。

> 授权的是一个 **Bot 身份**（`bot_type=3`、`ilink_appid: "bot"`），不是伪装客户端顶号 —— 这是它安全性的根本。

**收消息（长轮询，`src/monitor/monitor.ts`）**

- 循环 `POST /ilink/bot/getupdates`，带游标 `get_updates_buf`（存本地文件，可续传），服务端 hold 到有消息或 ~35s 超时。
- 支持文本/图片/语音/文件/视频；媒体走 CDN + AES-128-ECB 加解密（`src/cdn/`）。

**发消息（`src/messaging/send.ts`、`api.ts:sendMessage`）**

- `POST /ilink/bot/sendmessage`，回消息回传入站 `context_token` 维持上下文。
- 支持输入状态 `sendTyping`（先 `getConfig` 拿 `typing_ticket`）。

### 6.5 工程质量亮点

1. **凭证脱敏**：`src/util/redact.ts` 对日志 token/URL 脱敏，`Authorization` 打印成 `Bearer ***`。
2. **Stale token 保护**：服务端返回 `-14` 时暂停该账号 1 小时，避免用废 token 反复打接口触发风控。
3. **多账号**：一个网关挂多个微信号，按 `ilink_bot_id` 隔离。
4. **uint64 消息 ID 无损解析**：`parseWeixinApiJson` 手写扫描器，在 `JSON.parse` 前把大整数转字符串，避免 JS number 精度丢失。
5. **优雅停机**：`abortSignal` 立即中断长轮询；启停发 `notifyStart`/`notifyStop`。
6. **引用消息本地缓存**：新版微信只给 `svr_id` 时，用 `node:sqlite` 旁路存储还原上下文，缓存故障不影响主流程。

### 6.6 使用门槛与注意

- 必须跑在 OpenClaw 框架里（它是 channel 插件，非独立 SDK），需 Node.js ≥ 22.13.0。
- 登录后 `bot_token` 明文存 `~/.openclaw/openclaw-weixin/`，等于微信 Bot 控制权，**勿泄露、勿提交进 git**。

## 七、关于第三方 SDK（corespeed-io/wechatbot 等）

调研中还遇到一批把 iLink 封装成多语言 SDK 的第三方仓库（`corespeed-io/wechatbot`、`hxhlb/wechatbot2`、`epiral/weixin-bot`、`co-pine/wx-robot-ilink`）。判断：

- **底层协议 iLink 本身可靠**（官方能力）。
- 但这些是**第三方社区壳**，质量参差，需甄别。**首选官方 `Tencent/openclaw-weixin`**，第三方仅在"不想跑整个 OpenClaw、想要轻量 SDK 直连"时才考虑，且需自查：是否真对接官方 iLink、是否把登录态发往第三方服务器、star/issue/近期 commit 活跃度。

## 八、结论与建议

1. 做个人微信 AI 助理，**iLink（官方）是目前最可靠的路子**，合规且封号风险低。
2. 若已有基于 GeWeChat 的项目（如 personal-ai-pai），**把微信接入从 GeWeChat 迁移到 iLink/OpenClaw 是明确的升级方向**，可保留统一消息架构、只换适配层。
3. 小程序是另一条官方合规路径，但交互形态是独立小程序客户端，与"接管个人微信聊天"不是同一场景。
